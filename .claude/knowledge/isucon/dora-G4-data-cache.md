G4 は、データの持ち方とキャッシュである（旧 G3）。ロジック（[dora-G3-app-logic](dora-G3-app-logic.md)）を理解していないと安全に変えられない。
共通の凡例、前提構成は [dora-isucon-common](dora-isucon-common.md) にある。

## どこを見るか

1. **画像などの大きなデータを DB に持っていないか**
   - ファイルに書き出して nginx から配信する。
2. **HTTP のキャッシュ**
   - ベンチマーカーのソースで Cache-Control や 304 の扱いを確認する（private-isu は checker/action.go）。
   - 静的ファイルに `expires` を付けると、304 で済む。
3. **アプリのキャッシュ**
   - ログイン中のユーザー情報（セッションに入れる）。
   - 集計値（memcached やプロセス内のメモリ、世代番号で無効化）。
   - ベンチマーカーが /initialize で何を消すか（`DELETE ... WHERE id > N`）を確認し、無効化の範囲を決める。
   - マニュアルにある反映の猶予（何秒以内に反映すればよいか）を確認してから入れる。
4. **集計用のテーブルや、DB そのものの置き換え**
   - 毎回の集計を、書き込み時に更新するテーブルへ移す。
   - 集計に必要な形で持つ。MIN しか使わないなら最初の 1 行だけでよい（isucon12 の訪問履歴は 322 万行 → 20 万行）。
5. **キャッシュの捨て方は「版の番号」**
   - キーごとに版を持ち、更新の後で版を進める。読む側は読み始めたときの版を覚え、同じときだけ保存する。
   - これで、更新の前に読んだ古い値が、更新の後に保存されることはない。Go 1.18 のジェネリクスで共通の型にした。
6. **捨てる条件の洗い出し**
   - 追加、更新（終了、失格）、`/initialize` のそれぞれで何が変わるかを表にする。
   - 終了の直後など、遅れて記録される書き込みがある期間（isucon12 では 3 秒）は保存しない。
7. **キャッシュの粒度**
   - ページごとに持つと、ページの数だけ重い集計が走る。全件を持ってメモリで切り出す。
8. **リクエストごとの認証の処理**
   - 公開鍵の読み込みと解析、署名の検証を毎回していないか。検証済みのトークンを覚え、期限だけ毎回確かめる。

## 採用した設定・変更

### private-isu

| 対象 | 変更 | 状態 | 構成依存 | 効果・注意 |
|---|---|---|---|---|
| app + nginx | 画像を DB からファイルに書き出し、`try_files $uri @app` で nginx から配信 | 採用 | 同一ホスト | GET /image/* が SUM 268 秒 → 0.18 秒。app と nginx が別のホストならファイルの共有方法から考え直す |
| nginx | location の分割（ファイルの存在確認は `/image/ /css/ /js/ /img/ /favicon.ico` だけ） | 採用 | — | HTML を返す URL で、毎回ファイルを探さない |
| nginx | `expires 1d`（静的ファイルと画像） | 採用 | — | ベンチマーカーは Cache-Control の max-age を見て If-Modified-Since を送り、304 で成功になる（benchmarker/checker/action.go:160-191）。画像の 95% が 304 になった。効くかはベンチマーカーの実装次第 |
| app | ログインユーザーをセッションに入れる | 採用 | — | id / account_name / authority だけ。/initialize の後もログイン中に見える懸念は未検証 |
| app | コメント件数と最新 3 件を memcached にキャッシュ | 採用 | — | 世代番号で /initialize のときに全件を無効化（flush_all はセッションまで消す）。TTL 300 秒 |
| app | 投稿 1 件分の HTML 部品のキャッシュ | 見送り | — | CSRF トークンの差し込みが必要で、手間とリスクが大きい。app の CPU が上限なので、次の候補 |
| app | 投稿時に imgdata を DB に保存するのをやめる | 未実施 | — | 画像の fallback ルートが使えなくなる |
| nginx | `proxy_cache`（HTML のキャッシュ） | 見送り | — | ページにユーザーごとの CSRF トークンやユーザー名が入る |

### isucon12-qualify

| 対象 | 変更 | 状態 | 構成依存 | 効果・注意 |
|---|---|---|---|---|
| nginx | `etag off`、`expires 1d`（/css /js /img） | 採用 | — | 静的ファイルの配信を軽くする。etag off は private-isu の G6 の結論 |
| MySQL | 訪問履歴を「参加者ごとの最初の訪問」だけの表（主キーで `INSERT IGNORE`）にする | 採用 | — | 課金は MIN(created_at) しか使わない。322 万行 → 20 万行。SELECT visit_history が MySQL の 52% だった |
| app | ID の採番を MySQL の `REPLACE id_generator` からアプリの atomic カウンタに | 採用 | — | MySQL の 34%。起動時刻（ナノ秒）を初期値にすると、既存の ID とも再起動の前後とも重ならない |
| app | テナント DB の接続を使い回す | 採用 | SQLite | バーストで +29%。毎回閉じると WAL の書き戻しも毎回起きる。`/initialize` でファイルを差し替える前に全部閉じる |
| app | JWT の公開鍵を 1 回だけ読み、検証済みのトークンをキャッシュ | 採用 | — | 20,412 → 25,398。RSA の検証が 10%。exp と nbf は返すたびに確かめ、失敗したものは覚えない |
| app | テナントの行を name でキャッシュ | 採用 | — | 25,398 → 34,313。1 回 0.1ms でも毎リクエスト（7.7 万回）で MySQL の 60% |
| app | 記録済みの訪問を覚えて `INSERT IGNORE` を送らない | 採用 | — | → 約 38,800。冪等な書き込みなので、忘れても送り直すだけ |
| app | ランキングを大会ごとに全件キャッシュし、ページはメモリで切り出す | 採用 | — | ページごとのキャッシュだと、ページの数だけ集計が走った。バーストで 17 万点 |
| app | player、competition、大会の一覧、参加者の一覧、課金、参加者の詳細のキャッシュ | 採用 | — | すべて「版の番号」で書き込み時に捨てる（上の 5）。最低スペックでは誤差 |
| app | テナントのデータを SQLite から MySQL に移す | 見送り | SQLite | G3 と G4 の後では SQLite も MySQL も主なボトルネックでなくなった |
| SQLite | 初期データの重複したスコアの行を最新行だけにする | 未実施 | SQLite | 372 万行 → 約 20 万行の見込み。全件キャッシュがあれば効果は小さい |

## 完了条件

上位のエンドポイントで、毎回の重い集計やファイル I/O を、持ち方の変更やキャッシュで解消した。または解消しないと判断し、理由を記録した。
