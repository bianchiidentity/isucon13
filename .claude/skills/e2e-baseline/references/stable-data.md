# 期待値に使うデータの選び方

ISUCON の DB は常に動いている: ベンチを回すとテナント・ユーザー・投稿が増え、集計値が変わる。
「初期実装では通るが、ベンチを 1 回回したら落ちる」テストは回帰検出の役に立たない（誤検知でテストが信用されなくなる）。
期待値は「アプリの実装が正しい限り、ベンチを何度回しても変わらない値」から選ぶ。

## 安定している値（使ってよい）

- 初期データに含まれるエンティティの属性: 名前、ID、作成日時など
- **終了済み / 確定済み**のものに紐づく値: 終了した大会のランキング、締めた請求、過去の投稿のコメント数（追加不可なら）
- ベンチマーカーの整合性チェックにハードコードされた正解値
- 画面の固定文言: 見出し、テーブルのカラム名、ボタン名、説明文

## 不安定な値（避ける / 構造だけ見る）

- 一覧の先頭ページ（新しい順ソートだとベンチが作ったデータで埋まる）
- 全体の合計・件数（テナント全体の請求額合計、総ユーザー数など）
- 進行中のもの（未終了の大会、ライブ配信中の統計）
- 現在時刻に依存する表示

これらのページでは「見出し・カラム名が出る」「行が 1 件以上ある」「行の形式が正しい（数値に円が付く等）」といった構造のアサーションにとどめる。

## データの調べ方

実機の API を **GET で** 叩いて実データを見る。
初期データ由来かどうかは、ID の形式（初期データは連番やハッシュ、ベンチ作成分は UUID や大きい連番など）、
`initial_data/` や SQL ダンプとの突き合わせ、作成日時で見分ける。

```sh
curl -sk -c /tmp/ck -X POST -d 'id=...' https://<host>/<login>   # ログインして cookie を保存
curl -sk -b /tmp/ck https://<host>/api/... | python3 -m json.tool | head -50
```

期待値は数値の書式も含めて画面表示に合わせる（`toLocaleString()` で `960,300` になる、`円` が付く等）。

## 副作用に注意

- **GET でも書き込む API がある**。例: ランキング閲覧が閲覧履歴を INSERT し、請求額に影響する。
  ソースで GET ハンドラ内の INSERT/UPDATE を確認し、副作用があるなら「副作用が集計に影響しない対象」
  （終了済み大会など）だけを開く
- 更新系ボタンは押さない。初期状態の画面回帰チェックという目的には不要で、DB を汚して他のテストやベンチの結果を揺らす
- `POST /initialize` は勝手に叩かない。ベンチ実行中だと事故になる。初期状態に戻したいならユーザーに確認する
