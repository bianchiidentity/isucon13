# ISUCON E2E ベースライン生成

競技開始直後の **初期実装が正しい** 時点で、各ページの表示内容をアサーション付きの Playwright テストに固定し、
目視用のスクリーンショットも残す。以降の改修後に `npx playwright test` を再実行すれば、
画面が壊れたかどうかが Claude なしで数十秒でわかる状態をゴールにする。

判定の方針:
- **主はアサーション**（DOM・テキスト）。見出し、テーブルのカラム、初期データ由来の具体値、JS エラーや API エラーが起きていないこと
- **スクショは添え物**。ピクセル比較はしない。`e2e/screenshots/*.png` に上書き保存し、git の差分で「見た目が変わった画面」に気づけるようにする。
  ベンチを回すとデータが変わるので、ピクセル比較は誤検知だらけになり、テストが信用されなくなるため

時間の目安は 15〜20 分。競技時間は貴重なので、網羅性より「主要ページが確実に緑になる」ことを優先する。

## 手順

### 0. 接続先と実行環境を確認する

ユーザーに接続先 URL（ホストが複数あればすべて）を確認する。会話やメモ（`/etc/hosts`, `command.md` など）にあればそれを使う。

テンプレートを置いて依存を入れてから、環境チェックを回す:

```sh
cp -r <skill_dir>/assets/template e2e && mv e2e/gitignore e2e/.gitignore
cd e2e && npm install
bash <skill_dir>/scripts/check_env.sh "$(pwd)" https://<host1>/ https://<host2>/
```

NG が出たら、表示された修正コマンドをユーザーに実行してもらう。sudo が必要なコマンド（`playwright install-deps` など）は自分では実行せず、
ユーザーに `! <command>` で実行するよう頼み、終わったら再チェックする。待っている間に手順 1 を進めてよい。

### 1. 偵察する（読むだけ）

ページの一覧、ホストの分岐、認証の方法、各ページの API と表示内容を洗い出す。
やり方の詳細は `references/recon.md` を読むこと。特にベンチマーカーのコード（`bench/`）は、認証の方法と期待値の宝庫なので必ず見る。

結果は次の形の表にして、ユーザーに見せる（後で `e2e/README.md` にも載せる）:

| ホスト | パス | ロール | 動的パラメータ | 待つ要素 | アサーション |
|---|---|---|---|---|---|
| tenant | `/competition/:id` | player | 終了済み大会の ID | ランキングの 1 行目 | 1 位の名前とスコア |

### 2. 期待値に使うデータを決める

実機の API を GET で叩いて実データを見て、**ベンチを何度回しても変わらない値**を選ぶ。
判断基準と、GET なのに書き込む API などの落とし穴は `references/stable-data.md` を読むこと。

テストでは状態を変える操作をしない（追加・削除・完了・失格などのボタンは押さない）。また `POST /initialize` は叩かない。
初期状態の画面を記録するという目的には不要で、ベンチや他のテストを揺らすため。

### 3. テストを生成する

`e2e/tests/fixtures.ts` の `__TARGETS__` を実際のホストで置き換える:

```ts
export const targets = {
  tenant: process.env.E2E_TENANT_URL ?? 'https://isucon.t.example.local',
  admin: process.env.E2E_ADMIN_URL ?? 'https://admin.t.example.local',
}
```

ロールやホストごとに spec ファイルを分ける（例: `tests/player.spec.ts`, `tests/admin.spec.ts`）。
`test` と `expect` は必ず `./fixtures` から import する。このフィクスチャは JS 例外・`console.error`・自ホストへの 4xx/5xx・`alert` を自動で監視し、
発生したらテストを落とす。画面は出ているが裏で API が 500 を返している、という壊れ方を拾うため。
意図的にエラーを踏むテスト（未ログインで 401 になりリダイレクトする等）だけ、`allowProblems(/HTTP 401/)` で許可する。

1 ページあたりの型:

```ts
import { test, expect, snap, targets } from './fixtures'

test.describe('player', () => {
  test.beforeEach(async ({ page }) => {
    await page.goto(targets.tenant + '/')
    await page.locator('#account').fill('<初期データのプレイヤーID>')
    await page.getByRole('button', { name: '認証する' }).click()   // input[type=submit] も button ロール
    await expect(page).toHaveURL(/\/mypage$/)
  })

  test('大会詳細: 終了済み大会のランキング', async ({ page }) => {
    await page.goto(targets.tenant + '/competition/<終了済み大会ID>')
    const rows = page.locator('table tbody tr')
    // 読み込み完了を「実データの出現」で待つ。固定 sleep や networkidle には頼らない
    await expect(rows.first()).toContainText('<1位の名前>')
    await expect(rows.first()).toContainText('960,300')
    await expect(page.getByRole('heading', { name: 'スコアランキング' })).toBeVisible()
    await snap(page, 'tenant-player-competition')
  })
})
```

書き方の指針:
- ロケータは `getByRole` / `getByText` / 見出しやカラム名などユーザーに見える文言を優先する。CSS クラスに頼ると、改修でクラス名が変わっただけで落ちる。
  ただしユーザーから見て同じでも、壊れたら困る構造（テーブルの行など）は `table tbody tr` のように指定してよい
- アサーションは 1 ページあたり 2〜5 個。固定文言（見出し・カラム名）と、初期データ由来の具体値を最低 1 つずつ入れる。具体値がないと、空のテーブルでも通ってしまう
- `snap()` は読み込み完了を `expect` で待ってから呼ぶ。スクショの名前は `<ホスト>-<ロール>-<ページ>` にする。
  巨大な一覧でも git に載るよう、高さ 4000px で切っている。アニメーションは止めてあるので、同じ画面ならバイト単位で同一の PNG になる
- ログイン画面や未ログイン時のリダイレクトもページとして 1 本ずつ入れる
- ロールの切り替えが UI にあるなら（「管理者モードに切り替える」ボタン等）、UI 経由で切り替える
- 追加・作成系のモーダルやフォームは「開いて、入力欄が出ることを確かめ、キャンセルで閉じる」までをテストにする。送信はしない。
  モーダルも改修で壊れうる画面の一部で、開くだけならサーバの状態は変わらないため

### 4. 実行して安定させる

```sh
cd e2e && npx playwright test
```

初期実装に対するテストなので、**落ちたらまずテスト側を疑う**。失敗時は `test-results/` のスクショとトレースを見て、
待つ要素や期待値の書式（桁区切り、`円`、全角・半角）を直す。アプリ側の不具合に見える場合は、直さずにユーザーに報告する。

初期実装そのものが JS エラーや 4xx を出していることはよくある（例: 未ログインでページを開くと、リダイレクト前に API が 401 を返し、未処理の Promise 例外が出る）。
これは「初期状態の正しい振る舞い」として受け入れ、そのテストに限って `allowProblems(...)` で許可し、理由をコメントに書く。
許可は、エンドポイントまで含めたなるべく狭い正規表現にする。広く許可すると、改修で増えたエラーまで見逃してしまう。

すべて通ったら **もう一度実行** して、2 回連続で通ることを確認する（不安定なテストは、競技中に誤検知を生む）。
そのあと `screenshots/*.png` を Read で何枚か開き、ローディング表示ではなく実データが写っていること、日本語が豆腐（□）になっていないことを確認する。

### 5. 仕上げ

`e2e/README.md` に次の内容を書く:
- 実行方法（`cd e2e && npx playwright test`、接続先の環境変数）
- 手順 1 のページ表
- カバーしていないもの（更新系の操作、テストに使えなかったページとその理由）
- 偵察で見つけた初期実装の癖（例: 未ログイン時に 401 と未処理の例外が出る、マウント後の固定の待ち時間内に API が返らないと一覧が出ない、
  ソースとビルド済みバンドルでリンク先が違う）。改修後にテストが落ちたとき、テストの問題か、元からの挙動か、改修による劣化かを切り分ける手がかりになる
- 改修後の確認方法: テストが通ること＋`git status e2e/screenshots` で変わった画面を開いて目視する

コミットは、ユーザーに確認してから行う。`screenshots/` もベースラインとしてコミットする（`.gitignore` には入れない）。

最後に、ユーザーへの報告として以下を短く伝える。カバーしたページ数とテスト数、実行時間、期待値の根拠にしたデータ（例: 「終了済み大会 X のランキング」）、カバーしていないもの。

## 改修後に再実行して落ちたとき

この手順は生成後の運用の話だが、聞かれたら次のように切り分ける:
1. 失敗したアサーションと `problems` の添付（HTTP エラー・JS 例外）を見る
2. 同じ API を初期実装と現在の実装で curl し、レスポンスの差分を取る（キー名・型・ソート順・null と空配列の違いが典型）
3. スクショの差分を目視する
