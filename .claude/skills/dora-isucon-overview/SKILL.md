# ISUCON のサイトの全体像

ISUCON の問題のサイトを、マニュアルとソースコードから調べ、チーム全員が最初に読む 1 つの文書（全体像の文書）にまとめる。

## 目的

競技の開始直後に、チーム全員が同じ地図を持つこと。どこが重そうかを判断するのは、この文書を読んだ後に、計測で行う。

- **事実はソースコードとマニュアルから取る。** 書いたことには根拠（`ファイル:行`、マニュアルの節）を添える。
- **推測は推測と書く。** ISUCON のスキーマは外部キーを持たないことが多く、テーブルの関係は列名や JOIN から推定することになる。推定した関係は「推定」と明記する。
- **チューニングの提案はしない。** この文書は理解のためのもの。気づいたこと（N+1 らしいループ、インデックスのない検索など）は、最後の「気づいたこと」に事実として短く書くだけにする。
- **サーバーを変えない。** 読むだけにする。DB へのクエリも `SHOW`、`SELECT COUNT(*)`、`information_schema` の参照だけ。

## 手順

### 1. 置き場所を決める

- 作業名と出力先をユーザーに確かめる。既定は `memory/worklog/{作業名}/overview.md`（作業ログと同じディレクトリ）。
- チームで共有するなら、リポジトリ（例: `docs/overview.md`）にも置くかをユーザーに聞く。

### 2. 調べる

上から順に読む。全部を読み切る前に書き始めない。

| 対象 | 見るもの | 主に使う節 |
|---|---|---|
| マニュアル | サービスの説明、登場人物、採点（点の重いリクエスト、減点、失格の条件）、`/initialize`、反映の猶予、追試の条件 | 概要、採点と制約、ジャーニー |
| `webapp/` の構成 | 言語ごとの実装、Go の実装の場所、`go.mod`（フレームワーク）、フロントエンド（静的ファイル、SPA か） | アーキテクチャ |
| ルーティング | Go の main（`e.GET(`、`r.Get(`、`mux.HandleFunc(`、`router.Group(` などを grep）、ミドルウェア（認証、セッション） | エンドポイント、共通処理 |
| ハンドラ | 各ハンドラが読み書きするテーブル、外部への通信（別のサービス、外部コマンド、ファイル）。どのハンドラも先頭で呼ぶ関数（認証、セッションの読み込み） | エンドポイント、共通処理、通信の流れ |
| スキーマ | `webapp/sql/` の CREATE 文、初期化のスクリプト（`init.sh` など）、初期データ。MySQL 以外の DB（SQLite、Redis、PowerDNS の DB など）も | ER 図 |
| 実データ | 各テーブルの行数（`SELECT COUNT(*)`、または `information_schema.TABLES` の `TABLE_ROWS`） | ER 図 |
| ミドルウェア | nginx の server ブロック（location ごとの行き先、静的ファイル、upstream、TLS、HTTP/2）、systemd の unit、docker compose、環境変数のファイル（DB の接続先） | アーキテクチャ（nginx の振り分けを含む） |
| 構成 | サーバーの台数、それぞれで動いているプロセス（`systemctl list-units --type=service`、`ss -tlnp`） | アーキテクチャ |

フロントエンドの JavaScript が呼ぶ API の順番は、ユーザージャーニーの手がかりになる。

### 3. 書く

「文書の構成」の 8 つの節を、この順に書く。書き方の基準は `feedback_writing-granularity.md` に従う。

### 4. 確かめる

- エンドポイントの表の行数と、ルーティングに登録された数が一致するか数える。
- ER 図のテーブルの数と、スキーマの CREATE TABLE の数が一致するか数える。
- AA が等幅で崩れていないか（全角文字を枠の中に入れない。下の「AA の書き方」）。

### 5. 報告する

ユーザーには、文書のパスと、各節の要点を 1〜2 行ずつ返す。初回のベンチを回した後なら、エンドポイントの表に alp の回数や合計時間を足せることを伝える。

## 文書の構成

### 1. サイトの概要

- どんなサービスか（1〜2 文）
- 登場人物（一般ユーザー、管理者、配信者など）と、それぞれができること
- 主なデータ（ユーザー、投稿、ライブ配信など）
- 実装: 言語、フレームワーク、DB、フロントエンドの形

### 2. 採点と制約

作業の判断に直接使う制約をまとめる。キャッシュを入れるときは猶予を、失敗させてよいかは Critical を見る。

- 採点: エンドポイントごとの点数、点の重いリクエスト
- 減点と失格: エラーの扱い、Critical になるもの、打ち切りの条件
- `/initialize`: 何が戻るか（テーブルを作り直すのか、行を消すだけか）、タイムアウト
- 反映の猶予: どの書き込みが、どの読み取りに、何秒以内に反映されればよいか
- レート制限（429 を返してよいもの）、追試の条件

### 3. メインのユーザージャーニー

登場人物ごとに、典型的な操作の流れを番号付きで書き、各手順に呼ばれるエンドポイントを添える。ベンチマーカーが主に回す流れ（マニュアルの負荷走行の説明）を先に書く。

```text
配信を見る（視聴者）
1. ログインする            POST /api/login
2. 配信の一覧を見る        GET  /api/livestream/search
3. 配信に入る              POST /api/livestream/:id/enter
4. コメントを送る          POST /api/livestream/:id/livecomment
```

### 4. エンドポイント一覧

ルーティングに登録されたものを全部、1 行 1 エンドポイントの表にする。並びはルーティングの登録順か、ジャーニーの順。表の前には、ルーティングの場所と、列の読み方を 1〜2 文だけ書く。ミドルウェアや認証の説明は 7 節に書き、ここには書かない。

| メソッド | パス | ハンドラ | 内容 | 認証 | 読むテーブル | 書くテーブル |
|---|---|---|---|---|---|---|
| POST | `/api/login` | `main.go:812 loginHandler` | ログインしてセッションを作る | なし | users | sessions |

- 「認証」は、そのエンドポイントが求めるロールだけを書く（なし／ログイン／管理者など）。
- 「読むテーブル」には、どのリクエストでも共通処理で読むもの（セッション、ユーザー、テナントなど）を含めない。含めないことを表の前に書く。
- nginx が直接返すもの（静的ファイル）や別のサービスへ振り分けるものは、ここではなく 5 節の「nginx の振り分け」に書く。

### 5. アプリのアーキテクチャ（AA）

サーバー、プロセス、ポート、プロトコル、ソケットを箱と矢印で描く。複数台なら、どのサーバーで何が動いているかがわかるようにする。AA の後に、プロセスごとの補足（起動の方法、接続プールの上限、外部コマンド）と、nginx の振り分け（パスごとの行き先の表）を書く。

```text
+-----------+   HTTPS :443   +------------------------ isu1 -------------------------+
| benchmark | -------------> | +-------+  HTTP :8080  +------+  TCP :3306  +-------+ |
|  / user   |                | | nginx | -----------> | app  | ----------> | MySQL | |
+-----------+                | +-------+              | (Go) |             +-------+ |
                             |     |                  +------+                       |
                             |     | static files        |  DNS :53                  |
                             |     v                     v                           |
                             |  public/            +----------+                      |
                             |                     | PowerDNS |                      |
                             |                     +----------+                      |
                             +-------------------------------------------------------+
```

### 6. テーブルのスキーマ（ER 図の AA）

テーブルごとに箱を描き、主キー（PK）、外部キー（FK）、インデックス（IDX）、行数を書く。関係は線で結び、多重度（1、N）を書く。外部キーがなく列名や JOIN から推定した関係は、線の横に `(推定)` と書く。

```text
+----------------------+         +-------------------------+
| users  (1,000 rows)  |         | livestreams (7,500 rows)|
+----------------------+         +-------------------------+
| PK id          BIGINT| 1     N | PK id            BIGINT |
|    name       VARCHAR|---------| FK user_id       BIGINT | (推定)
|    display_name      |         |    title        VARCHAR |
+----------------------+         | IDX (user_id)           |
                                 +-------------------------+
```

テーブルが多いときは、関係の多いテーブルを中心に、関係でまとまるグループに分けて描く。列が多いテーブルは、キーと、関係や検索に使う列だけを描き、「ほか n 列」と書く。

### 7. リクエストの共通処理

すべて（または大半）のエンドポイントに共通してかかる処理をまとめる。認証やテナントの解決は、全リクエストの固定費になりやすい（isucon12 では JWT の検証がアプリの CPU の 10%、テナントの SELECT が MySQL の 60%）。8 節のシーケンス図を読む前提になるので、その直前に置く。

- ミドルウェアの一覧（`ファイル:行`）
- 認証とセッション、テナントやユーザーの解決の手順を、番号付きで書く（何を読み、何を確かめ、失敗したら何を返すか）
- 「どのリクエストでも毎回かかるもの」の表（処理と、対象のエンドポイント）

### 8. 通信の流れ（AA）

主なジャーニー 1〜3 本について、リクエストが nginx、app、DB、外部のサービスをどう通るかを、シーケンス図で描く。1 回のリクエストで発行するクエリの数（ループの中のクエリなど）も書く。7 節の共通処理も図に含め、節の最初に「どの図も最初の数行は 7 節の共通処理」と書く。

```text
client          nginx           app                    MySQL
  |  POST /api/   |               |                       |
  |  livestream/  |               |                       |
  |  1/enter      |               |                       |
  |-------------->|-------------->|                       |
  |               |               |-- SELECT sessions --->|
  |               |               |-- SELECT livestreams->|
  |               |               |-- INSERT viewers ---->|
  |               |<--------------|                       |
  |<--------------|  201          |                       |
```

### （最後に）気づいたこと

調べている間に目についた事実を、箇条書きで短く書く（例: 「`GET /api/livestream/search` はタグの数だけ SELECT を発行する（`livestream_handler.go:120`）」）。原因の分析や改善案は書かない。

## AA の書き方

- コードブロックの言語は `text` にする。
- 枠と線は半角の `+ - | > < v ^` だけで描く。罫線の記号（`┌─┐`）は使わない（表示する環境によって幅が変わる）。
- 枠の中に全角文字を入れない。日本語の説明は枠の外に書く。全角文字は表示の幅が 2 になり、枠がずれる。
- 横幅は 100 文字以内にする。収まらなければ、図を分ける。
- 描いた後、各行の長さをそろえたいところで数え、枠が閉じているかを確かめる。

## 更新するとき

- この文書は、調べた時点の記録である。スキーマやエンドポイントを変えたら、変えた箇所だけを直し、文書の先頭に更新した日時と、何を変えたかを 1 行書く。
- 初回のベンチの後は、エンドポイントの表に alp の回数、合計時間、平均時間の列を足すと、どこから手を付けるかが見えやすい。
