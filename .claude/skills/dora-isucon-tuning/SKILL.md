# ISUCON チューニング

ISUCON のアプリを、計測に基づいて段階的にチューニングする。このスキルが決めるのは**チューニングの進め方**である。ジャンルごとのナレッジは、このリポジトリの `.claude/knowledge/isucon/` にある。

## 目的: 人間が判断し、理解できるチューニング

ユーザーが ISUCON に参加するのは学習のためである。スコアも目指すが、優先するのは、Claude が行ったチューニングを**人間が判断し、理解できること**である。この目的から、次の原則が決まる。

- **推測で直さず、まず計測する**
  - 変更の根拠は、alp、スロークエリログ、プロファイラ、CPU 使用率などの数値で示す。
- **変更は 1 回に 1 つ、提案して GO を待つ**
  - 同時に複数を変えると、どれが効いたかを人間が判断できない。
  - 提案には「観測した事実」「遅い理由の仕組み」「変更内容」「期待する効果」「リスク」を含める。
  - 例外は G1 の base-conf で、検証済みの設定を一度に入れる。
- **結果を仮説と突き合わせる**
  - 効いた／効かなかったで終わらせず、仮説が当たったか、外れたならなぜかを書く。
  - スコアが伸びなかった変更も、理由と一緒に記録する。
- **一般化できる学びはナレッジに還元する**
  - 「構成依存」の有無と前提も添えて、該当するジャンルのファイル（[dora-G0-measurement](../../knowledge/isucon/dora-G0-measurement.md)〜[dora-G7-final](../../knowledge/isucon/dora-G7-final.md)）への追記をユーザーに提案する。

## 起動したときの手順

このスキルは、競技の開始直後にも、後半に開いた新しいセッションにも起動される。**「最初に〇〇をする」とは考えず、進捗ファイルと実環境から今の段階を判断する**。完了条件を満たした作業はやり直さない。

1. **作業名を決める**
   - `memory/` 配下の `progress.md` を探す（置き場所は「進捗ファイル」の節）。候補が 1 つならそれを使ってよいかユーザーに確かめる。無ければ作業名を聞く。
2. **進捗ファイル `progress.md` を読む**
   - 書式は「進捗ファイル」の節にある。
   - 無い場合も「初回」と決めつけない。手順 3 で環境を見て、既に済んでいる作業がないか確かめる。
   - 2026-10-18 より前の進捗ファイルは、ジャンルが旧番号である（[dora-isucon-common](../../knowledge/isucon/dora-isucon-common.md) の対応表）。
3. **実環境と突き合わせる**（軽い確認だけにとどめる）
   - `git log --oneline -20` と「適用中の変更」を照合する。前のセッションが記録の前に終わっていることがある。
   - 計測結果のディレクトリで、最新のベンチの日時とスコアを確かめる。
   - アプリ、nginx、DB が動いているかを確かめる。
   - G1 の base-conf が入っているか（`/etc/nginx/conf.d/isucon.conf`、`/etc/mysql/mysql.conf.d/zz-isucon.cnf`）を確かめる。
   - 食い違いがあれば、推測で埋めずにユーザーに報告する。
4. **次の一手を決める**
   - 最後の変更より後にベンチを回していなければ、まずベンチを回して計測する。
   - それ以外は「ジャンルと順番」の規則で、次に取り組む対策を選ぶ。
5. **ユーザーに報告して GO を待つ**
   - 今の段階、最新のスコアとボトルネック、次の一手の提案を短くまとめる。

## ジャンルと順番

チューニングは次の 8 ジャンルに分ける。分け方の軸は「その変更が、他の何かが決まらないと値を決められないか」である。後ろのジャンルほど、前のジャンルの結果に依存する。ジャンルごとに見る箇所と過去の採用・却下は、各ジャンルのファイルにある。

| # | ジャンル | 例 | 依存するもの | ナレッジ |
|---|---|---|---|---|
| G0 | 計測・運用の基盤と仕様の把握 | bench スクリプト、プロファイラ、git 管理、マニュアルの要点、ベースラインのスコア | なし | [dora-G0-measurement](../../knowledge/isucon/dora-G0-measurement.md) |
| G1 | どの環境でも最初に入れる設定 | `script/base-conf/apply.sh`（自動アップデートの停止、alp と pt-query-digest、LTSV、fd の上限、MySQL の耐久性の設定、スロークエリログ） | なし | [dora-G1-base-conf](../../knowledge/isucon/dora-G1-base-conf.md) |
| G2 | 前提に依存しない確実な改善 | インデックス、明らかな初期設定の誤り（開発モード、ワーカー 1） | なし（クエリの形にだけ依存） | [dora-G2-safe-improvements](../../knowledge/isucon/dora-G2-safe-improvements.md) |
| G3 | アプリのロジック | N+1、LIMIT、`SELECT *`、不要なロック、外部コマンド、プレースホルダの展開 | G2（直すとクエリの形が変わる） | [dora-G3-app-logic](../../knowledge/isucon/dora-G3-app-logic.md) |
| G4 | データの持ち方・キャッシュ | 別の DB への移行、BLOB をファイルにする、集計テーブル、キャッシュ、ID の生成方法 | G3（ロジックを理解していないと安全に変えられない） | [dora-G4-data-cache](../../knowledge/isucon/dora-G4-data-cache.md) |
| G5 | サーバー構成・接続経路 | 複数台への振り分け、DB を別のサーバーに分ける、UNIX ドメインソケット | G4（何が重いかが決まらないと分け方を決められない） | [dora-G5-topology](../../knowledge/isucon/dora-G5-topology.md) |
| G6 | リソース配分・細かいパラメータ | ワーカー数、コネクションプール、max_connections、buffer_pool、nginx のバッファ、カーネル | G5（台数、CPU、メモリ、データ量） | [dora-G6-resources-params](../../knowledge/isucon/dora-G6-resources-params.md) |
| G7 | 最終調整 | ログの停止、再起動試験 | すべて（計測できなくなるので最後） | [dora-G7-final](../../knowledge/isucon/dora-G7-final.md) |

G1 には、構成に依存せず、入れて困ることがほぼない設定だけを入れる。値を計測して決める設定は G6 で入れる（例: スロークエリログは G1 で ON から始め、G7 で OFF にする。open_file_cache は G1 に入れず、G6 で計測してから入れる）。

### 対策の選び方

ジャンルは厳密な一本道ではない。毎回、次の規則で選ぶ。

0. **G1 を入れた直後に、G2 の「明らかな誤り」を一通り確かめる**（開発モード、ワーカー 1、開発用のリクエストログやデバッグ出力）。計測の上位に出ていなくても、クエリのチューニングより先に提案する。
   - 開発用のログは計測に使わないのに、CPU と計測の経路（journald）を食う。isucon11 では気づくのが遅れ、その間の接続プールの統計とエラーの集計が欠けていた（[dora-G2-safe-improvements](../../knowledge/isucon/dora-G2-safe-improvements.md)）。
1. 最新の計測で、最も時間や CPU を使っている箇所を 1 つ選ぶ。
2. その箇所への対策がどのジャンルに属するかを判定する。
3. 同じ箇所に、より前のジャンルの対策が残っていれば、そちらを先にする。
   - 例: ランキングが遅い原因が N+1（G3）とキャッシュの不在（G4）なら、N+1 から直す。
4. G3 の変更でクエリの形が変わったら、G2 に戻ってインデックスを見直す。
5. **G6 のパラメータは、G5 で構成を決めるまで調整しない**。
   - 例外: G2 の「明らかな誤り」（ワーカー 1 など）は先に直してよい。最適な値は G6 で決め直す。
   - 例外: ユーザーが先に進めてよいと言ったとき。
6. 1 台の CPU が上限に張り付いて計測にならないときは、G5 を前倒しにする。前倒しにするときはユーザーに理由を説明する。
7. 実サービスではやらない対策（点の高いリクエストの優先、プロトコルの切り替えなど）は、演習では「本番向け」と分けて提案し、実施しない。

### MySQL の設定は 4 種類に分ける

MySQL のチューニングは、入れる時期が違う 4 種類に分かれる。

| 種類 | 例 | 時期 | 理由 |
|---|---|---|---|
| 耐久性を捨てる設定 | `skip-log-bin`、`innodb_flush_log_at_trx_commit`、doublewrite | G1 | 他に依存しない。正常に再起動すればデータは残る。base-conf が入れる |
| スキーマ・インデックス | `ADD INDEX`、複合インデックス、型 | G2 | 設定と無関係に効く |
| 接続の方法 | UNIX ドメインソケット / `interpolateParams` | G5 / G3 | ソケットは同じホストのときしか使えない。プレースホルダの展開はアプリ側の変更 |
| リソース配分 | buffer_pool、max_connections、log_file_size | G6 | DB のサーバー、メモリ、データ量、app の台数が決まってから |

performance_schema とスロークエリログの停止は G7 に回す。計測に使うからである。逆に、アプリの開発用のリクエストログは計測に使わないので、G7 を待たずに G2 で外す。nginx も同じ考え方で、LTSV のログと fd の上限は G1、静的ファイルの配信と `expires` は G4、upstream の振り分けは G5、バッファや open_file_cache は G6 に入れる。

### ジャンルの完了条件

「完了」は、そのジャンルにもう着手しないという意味ではない。次のジャンルへ進んでよい状態を指す。

- G0: ベンチを 1 コマンドで回せる。マニュアルの要点が進捗ファイルにある。ベースラインのスコアを記録した（G1 を入れる前に測る）。
- G1: 全サーバーで base-conf を適用し、`nginx -t` と MySQL の値を確かめた。alp と DB のクエリ集計が結果のディレクトリに残る。ベースラインと比べたスコアを記録した。
- G2: 上位のクエリに Table scan（SQLite なら `SCAN`）が残っていない。明らかな誤りを直した。
- G3: 上位のエンドポイントに N+1 と不要なロックが残っていない。
- G4: 上位のエンドポイントで、毎回の重い集計やファイル I/O を、持ち方の変更やキャッシュで解消した。または解消しないと判断し、理由を記録した。
- G5: 各サーバーの役割が決まり、進捗ファイルの「環境」に書いた。
- G6: 各サーバーの CPU とメモリを見て、ワーカー数、プール、DB のメモリを決めた。
- G7: 再起動後にベンチが通り、データが残っていることを確かめた。

## 1 回の改善サイクル

1. 計測する（ベンチ、alp、DB のクエリ集計、CPU）。
2. 「対策の選び方」で対策を 1 つ選び、ジャンルを判定する。
3. ユーザーに提案する。観測した数値、遅い理由の仕組み、変更内容、期待する効果、リスクを示す。
4. GO が出たら適用する。コードと設定は git にコミットする。コミットメッセージにジャンルを書く（例: `G2: visit_history に index を追加`）。
5. 回帰を確認する（[dora-isucon-common](../../knowledge/isucon/dora-isucon-common.md) の「変更するたびに確認すること」）。
6. ベンチを回し、結果を仮説と突き合わせる。計測値は、複数回測ったなら平均を、1 回だけならその値と前の回との差を書く。
   - 1 つの変更につき 2〜3 回で十分。同じ条件（AWS t3 なら、クレジットが残っているか切れているか）の回どうしで比べる。
   - 条件をそろえるためだけにベンチを回し続けない。
   - **スコアが下がったら、負荷の量も前の回と比べる**（ユーザーの増加の通知、登録の件数、書き込みの回数）。ボトルネックを直すとベンチマーカーが負荷を増やし、次のボトルネックが出て下がることがある。負荷が増えて下がったなら、取り消しを提案せず、次に詰まった箇所を提案する（`dora-feedback_keep-bugfix-when-load-grows`）。
7. 進捗ファイルを更新する。

### 守ること

- **却下されたパラメータは試さない**（各ジャンルのファイルで「却下」のもの）。
- **ナレッジの値をそのまま流用しない**。「構成依存」に印がある行は、今の構成で計測し直して決める。
- **ベンチ中に重い作業を並行して走らせない**。ビルドや集計はベンチの前後に行う。
- **Claude Code 自身もサーバーのメモリを使う**。G6 でメモリを配分するときは、その分を差し引く。

## 進捗ファイル

`progress.md` は、どのセッションからでも続きを再開するための状態ファイルである。過程は残さず「今の状態」だけを書き、古い情報は上書きする。

- 置き場所: Claude Code のメモリのディレクトリ（`~/.claude/projects/<作業ディレクトリ>/memory/`。以下 `memory/`）の `memory/{作業名}/progress.md`。人ごと、サーバーごとに分かれる。リポジトリには入れない
- 更新するとき: 変更を適用したとき、取り消したとき、ジャンルを移ったとき、ベンチを回したとき、セッションを終える前
- 進捗ファイルの更新は、確認を取らずに行ってよい。更新したことはユーザーに伝える

書式:

```markdown
# {作業名} 進捗

最終更新: YYYY-MM-DD hh:mm（JST）

## 環境

- サーバー: {ホスト名、IP、役割}
- アプリ: {実装言語、ソースの場所、再起動の方法}
- 計測: {bench スクリプトのパス、結果のディレクトリ}

## 仕様の要点

- 採点: {点数の重いエンドポイント、減点の条件}
- 初期化: {/initialize で何が戻るか}
- 反映の猶予: {キャッシュしてよい範囲}
- 追試: {再起動後の条件}

## ジャンルの状態

| ジャンル | 状態 | メモ |
|---|---|---|
| G0 | 完了 | ベースライン 239 |
| G1 | 完了 | base-conf を app と db に適用。239 → 410 |
| G2 | 進行中 | visit_history の index は済み |
| G3 | 未着手 | |

## 適用中の変更

| # | ジャンル | 変更 | コミット | 計測（前 → 後） |
|---|---|---|---|---|

## 取り消した・却下された変更

- {変更}: {理由}

## 最新の計測

- {日時}、スコア {値}、上位のボトルネック {エンドポイントやクエリ}

## 次の候補

1. {対策}（{ジャンル}、根拠: {数値}）
```
