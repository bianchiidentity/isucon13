# pprotein から改善 Issue を3件作る

目的は、担当者が「画面のどの操作の、どの処理を、なぜ高速化するのか」を理解して、互いに変更をぶつけにくい3件に着手できること。

この skill の実行依頼には、対象リポジトリへの Issue 作成を含む。作成前の確認待ちは挟まない。skill 自体の作成・編集依頼では Issue を作成しない。実装・ベンチ実行・新規プロファイル収集・デプロイ・Project 操作は含まない。

## 1. 対象の画面と計測を確定する

- ユーザー指定の pprotein URL・計測グループ・結果を優先する。未指定なら作業リポジトリの設定・記録・接続済み画面から探し、接続先や Issue の投稿先を決められないときだけ質問する。他の練習環境の値を持ち込まない。
- ブラウザで pprotein の対象グループと HTTP・slow query・CPU の画面を確認する。集計の詳細は、画面に対応する API やエクスポートも使ってよい。画面が使えない場合は API・保存結果を使ったことを明示し、画面を見たと書かない。
- 日時とタイムゾーン、ベンチ結果・成否、Group ID、Snapshot ID・対象ホスト・収集状態、分かれば稼働リビジョンを記録する。API の並び順だけで最新を決めない。同じグループでも収集時間が負荷走行と合っているか確認する。
- 異なるベンチの HTTP・SQL・CPU を混ぜない。対象が欠ける場合は不足を明記する。失敗ベンチなら性能改善より失敗原因の切り分けを優先し、成功時の性能を断定しない。
- API は導入版の画面やソースから確認する。`GET /api/group/collect` は収集を開始するため呼ばない。

## 2. 負荷上位を画面操作と実コードへつなぐ

まず HTTP の累積時間上位と slow query の累積 QueryTime 上位を各5件程度読み、必要な分だけ広げる。HTTP は method・正規化した path・回数・累積/平均時間・利用可能なら P95/P99 とエラー内訳を、SQL は正規化クエリ・回数・累積/平均時間・利用可能なら走査行数と LockTime を取得する。CPU が関連する場合は flat/cumulative と呼出経路を確認する。単位と集計元を残す。

各候補について次のつながりをコードで追う。

**画面・ユーザー操作 → フロントのイベント/API 呼出し → HTTP method/path → ルート・ハンドラ → 呼出関数・SQL → テーブル/索引/待機処理**

- フロント・テンプレート・仕様・ベンチシナリオを調べ、「一覧を開く」「検索条件を変える」など実際の操作と、その操作で何を読み書きするかを説明する。画面がない API は利用者・ベンチの操作として書き、架空のボタン名を作らない。操作との対応を確認できなければ未確認とする。
- 集計に出た SQL と実コードの呼出元を照合する。共通 SQL が複数のエンドポイントから呼ばれる場合、その範囲を記載し、SQL の全時間を一つのエンドポイントに帰属させない。
- 計測時のコードが分かればその版を見る。現在の作業ツリーと稼働版の差を確認し、既に改善済みの古い処理を新規課題にしない。HEAD だけを見て稼働版を断定しない。
- 実コードをファイル名・関数名・行番号とともに短く抜粋する。ループ内 SQL、余分な取得、走査範囲、ロック区間など、遅い仕組みが読み取れる範囲を選ぶ。SQL はコピー可能なコードブロックにする。
- 観測事実と原因の仮説を分ける。HTTP と SQL の累積時間、CPU の親子 cumulative は足さない。LockTime や走査行数の未計測の0を根拠にしない。未測定の改善点数を予測しない。

## 3. 負荷が大きく競合しにくい3件を選ぶ

既存の open Issue と進行中 PR を読み、重複・実装中・依存する変更を把握する。同じ目的の Issue がある場合は新規に重複作成しない。既存 Issue を再利用する場合は最終報告で区別し、明示依頼なしにその本文や状態を変更しない。

順位は、同じ計測グループ・同じ対象範囲での **HTTP 累積時間の降順**と **slow query 累積 QueryTime の降順**を別々に記録する。HTTP は method と正規化 path、SQL は正規化クエリを単位とし、画面にフィルターがある場合はその範囲を明示する。選んだ3件の中での順番を負荷順位として書かない。同値は同順位とし、順位付けの範囲や値が不足している場合は未確認とする。

各 Issue には「HTTP の累積時間で上から2番目」「slow query の累積 QueryTime で上から4番目」のように、指標と元の順位を平易に書く。一つの課題に複数のエンドポイント/SQL がある場合は、それぞれの順位を残す。CPU 主体なら指標（flat など）と対象関数の順位を明示し、HTTP/SQL と混ぜた総合順位を作らない。

候補ごとに「計測上の順位・主要負荷・変更予定のファイル/関数・SQL/テーブル/索引・共通処理・先行依存」を比較し、負荷と根拠の強いものから選ぶ。3件の組合せで次を評価する。

- 同じ関数、近接した編集範囲、共通ヘルパー、同じスキーマ/マイグレーション、同じ設定を同時に変更する候補は避ける。
- ファイルが別でも、同じ SQL の形と索引、キャッシュと更新処理など相互に前提を変える候補は独立扱いしない。
- 同じファイルでも別の関数なら、その範囲と共通部分への影響を確認して判断する。「別エンドポイントだから競合しない」で済ませない。
- 上位候補が重なるなら、次の負荷上位で独立した候補へ進む。単純順位の上位3件との差と選外理由を残す。軽微な課題で数だけそろえない。
- 各 Issue には並行作業で触る範囲・触らない共通部分・依存関係を書く。共通ファイルへの小さな登録変更が避けられない場合は、競合の可能性と取り込み順を明示する。競合ゼロを保証しない。

原則は3件。裏付けのある独立した候補が3件なければ、確認できた分だけ作成し、不足理由と追加で必要な情報を報告する。

## 難易度ラベル

各 Issue に `easy`・`normal`・`hard` のうち必ず1つを付ける。負荷の順位や期待効果ではなく、実装・仕様理解・検証の難しさで決める。

| ラベル | 判定基準 |
|---|---|
| `easy` | 局所的な変更で完結し、既存の挙動を保つ方法と確認方法が明確。例: クエリと索引の対応が明確な索引追加、単純な重複処理の削減 |
| `normal` | 複数の関数やSQLの変更、仕様の確認が必要だが、既存の構成で実装・検証できる。例: 順序・件数・権限を保つN+1解消、取得処理の組み替え |
| `hard` | 並行実行・整合性・キャッシュ無効化・データ移行・複数台構成など、広い影響範囲や難しい検証を伴う |

例だけで機械的に分類せず、実際の変更範囲と守る仕様で判断する。難易度の根拠が未確認なら、その不確実性も本文に書く。3件の難易度を均等にするために選定を変えない。

## pprotein のスクリーンショット

各 Issue に、根拠となる pprotein の画面を原則1〜2枚添える。HTTP の順位・時間が分かる一覧と、該当 slow query の SQL・集計値が分かる詳細など、課題の裏付けに必要な画面を選ぶ。CPU 主体なら対応するプロファイル画面を使う。

- 対象グループ・ホスト・並び順・フィルターを確かめ、読み込み完了後にブラウザのスクリーンショット機能で取得する。画像を生成して計測画面の代わりにしない。
- 対象行・列名・数値・ソート順が読める範囲で撮る。順位が画面に表示されない場合は一覧から順位を確認し、数えた対象範囲を本文に書く。切り抜いた画像だけから全体順位を断定しない。
- キャプションに「何の画面か」「対象 endpoint/SQL」「指標・順位」「Group/Snapshot ID」を添える。同じ根拠画面は複数 Issue で再利用してよい。
- Cookie・トークン・個人情報・機密の SQL リテラルなどが写らないよう確認する。必要なら取得範囲を変えるか、機密部分だけをマスクし、マスクしたことを明記する。計測値・順位は書き換えない。
- 画像は Git 管理外の一時ディレクトリへ保存する。画面のローカルURLやローカルファイルパスだけを Issue に貼らない。

### Issue から見える形で保存する

既存の画像公開方式がリポジトリにあれば従う。なければ、今回の Issue 用スクリーンショットの掲載として、対象リポジトリの専用 GitHub Release `pprotein-evidence` に添付してよい。これは skill 実行時の画像掲載に含む。

- 新規 Release は既存のコミットを明示して作り、アプリ用のコミットやリリースを新たに作らない。専用タグが既にあれば再利用し、タグを付け替えない。通常の最新版リリース扱いにしない（`--latest=false`）。
- ファイル名は計測グループ・対象・内容ハッシュから一意にし、既存の画像は上書き・削除しない。同一内容の添付済み画像は再利用する。
- Release の添付 URL を Issue の Markdown 画像として掲載し、アップロード後に URL から画像を取得・表示して確認する。private リポジトリの画像は権限のある読者が閲覧できる範囲で扱い、外部公開サービスへ転送しない。
- 画面にアクセスできない場合はスクショ未取得と書く。アップロードできない場合はローカル画像を保持して掲載未完了と報告し、架空の画像URLを貼らない。いずれの場合も、取得済みの計測値と実コードで裏付けられる Issue の作成は進める。

画像は補助資料とする。endpoint・SQL・数値・順位・実コードは本文のテキストにも残し、画像だけを根拠にしない。

## 4. Issue 本文

タイトルは `[性能] <画面操作/機能>: <減らす処理>` とし、各 Issue が単独で理解できる本文にする。次の構成を使い、空欄や架空の数値を埋めない。

```markdown
## 何を速くするか
<利用者がどの画面で何をすると、裏側で何が行われ、どこに時間がかかるか。専門用語だけにせず2〜4文で説明>

## 対象と計測根拠
- 操作: <画面・操作。フロント/仕様/ベンチの根拠リンク>
- エンドポイント: `<METHOD /path>` → `<handler>`
- 負荷順位: <例: HTTP の累積時間で上から2番目、slow query の累積 QueryTime で上から4番目。計測対象範囲・フィルターも記載>
- slow query: <クエリの識別子/集計画面へのリンクと、下記のSQL>
- HTTP: <回数、累積時間、平均、分位点、エラー。取得できた値と単位>
- SQL: <回数、累積/平均時間、走査行数など。取得できた値と単位>
- 計測: <日時・TZ、ベンチ結果、Group/Snapshot ID、ホスト、コードの版と未確認事項>

## pprotein の画面
<アップロード済み画像のMarkdownとキャプション。未取得・未掲載ならその理由>

## 現在の処理と遅くなる理由
<操作 → HTTP → 関数 → SQL の順序。観測事実と原因仮説を区別>
<実コードの出典リンク・関数名・行番号と、該当言語の短いコードブロック>
<該当するSQLのコードブロック。値や機密情報は伏せ、構造を保つ>

## 改善方針
<どの処理・回数・走査・待機を減らすか。必要なら変更後の短いコード例>
<変更後の例は「実装案」と明記し、現在の実コードと混同しない>

## 難易度
`<easy / normal / hard のいずれか>` — <実装・仕様・検証の観点から具体的な理由>

## 変更範囲と並行作業
- 変更予定: <ファイル・関数・テーブル・索引など>
- 共通部分への影響/他候補との重なり: <確認結果>
- 依存・取り込み順: <なし、または具体的な条件>

## 確認方法
- <守る仕様: 権限、並び順、ページング、更新整合性など今回に関連するもの>
- <同条件の成功ベンチで比べる値: 対象HTTP時間、SQL回数/走査など>
- <関連する既存テストや失敗条件>
```

slow query がない CPU/I/O 主体の課題は「slow query: 該当なし」または「未取得」と根拠を書き、対応する関数・待機処理を示す。SQL とエンドポイントの対応を推測で作らない。

## 5. 作成と確認

- 投稿先の既存ラベルを確認し、選んだ難易度ラベルがなければ作成する。既存ラベルの色や説明は変更しない。新規作成時の説明は `easy`: 「局所的で実装・検証方法が明確」、`normal`: 「複数箇所の変更や仕様確認が必要」、`hard`: 「整合性・並行実行・構成変更など検証が難しい」とする。
- 投稿先は今回の作業リポジトリを確認し、`gh issue create --repo OWNER/REPO --title ... --body-file ... --label easy`（難易度に応じてラベルを指定） などの構造化された入力を使う。本文をシェルコードとして展開しない。
- 投稿直前に重複候補を再確認する。3件にはそれぞれ `<!-- pprotein-issues:GROUP_ID:STABLE_TARGET -->` の識別子を入れ、再実行時に同じ計測・対象で重複投稿しない。STABLE_TARGET は endpoint/SQL/変更対象から一貫したものを決める。
- 作成に失敗したら Issue 一覧を読み直し、成功済みを確認してから未作成分だけ再試行する。権限や接続の問題が続く場合は本文案を残し、作成済みと未作成を報告する。
- Issue を読み戻し、実コード・SQL・リンク・画像の表示・キャプション・改行と、本文に一致する難易度ラベルが1つだけ付いているか確認する。必要な範囲で今回作成した本文だけを修正する。ログ全文・認証情報・個人情報は公開しない。
- 最終報告には3件のリンク、負荷順位・難易度と選定理由、互いに変更が重なりにくい理由、見送った上位候補と未確認事項を短く示す。
