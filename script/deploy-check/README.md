# deploy-check

変更の前後で、決めたリクエストの応答が変わっていないかを確かめる（回帰の確認）。入口はリポジトリ直下の `./deploy-check`。デプロイそのものはしない。
キャッシュやクエリの書き換えで応答の中身を変えてしまったことを、ベンチより早く、どの項目が変わったかまで見つけるためのもの。

```bash
./deploy-check --before   # 変更の前（前回の deploy の後）に、応答を保存する
./deploy                  # 変更を反映する
./deploy-check --after    # 同じリクエストを送り、保存した応答と比べる。違えば差分を出して終了コード 1
```

## 考え方

- **比べるリクエストは `paths.txt` に書く。** 問題ごとに、主要なページと API を選ぶ。書き方は paths.txt の先頭のコメント。
- **ログインは自動。** paths.txt に `login` の行を書くと、受け取った Cookie が以降のリクエストに付く。実行のたびにログインし直すので、Cookie の期限は気にしなくてよい。
- **比べるもの。** どの種類も、ステータス、Content-Type、`header=` で指定したヘッダ（仕様で決まった `Cache-Control` など）を比べる。本文は、JSON なら `jq -S` で整形してから（キーの順や空白、インデントの違いは差分にならない）、静的ファイルなら sha256 で比べる。
- **毎回変わる項目は、行ごとに jq の式で除く。** 時刻、採番した ID、トークンなど。除かないと、正しい変更でも差分になる。

## 実行する前に

- **既定では、`/initialize` を呼んでデータを初期化してから送る**（paths.txt の `init` の行）。同じデータに同じリクエストを送ったときの応答を比べるため。初期化には数秒〜数十秒かかる。
- 初期化したくないとき（読み取りだけの確認、今のデータのまま比べたいとき）は `--no-init`。保存と比較の両方を `--no-init` にする（片方だけだと警告が出る）。
- 書き込みのリクエスト（POST など）を書くと、送るたびにデータが変わる。`--no-init` と一緒に使うと、2 回目以降の応答は 1 回目と違ってくる。
- **`--before` の後で paths.txt を変えると、`--after` は止まる。** 保存したファイルを行の順番で対応づけているため。行を足したら、変更の前の状態で `--before` からやり直す。
- ベンチの最中や、2 人で同時に実行しない。初期化でベンチが壊れ、保存した応答も上書きし合う。
- paths.txt の行はシェルとして解釈される（`$(...)` を書くと実行される）。チームで書くファイルなので、そのまま受け入れている。
- jq が要る（G1 の base-conf で入る）。応答は `results/deploy-check/before/` と `after/` に置く。`results/` は git に入れない。
